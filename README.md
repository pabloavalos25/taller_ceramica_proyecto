# SUYAI

Proyecto en desarrollo: aún no es una aplicación funcional ni está listo para producción. El acceso y el cambio de contraseña cuentan con integración experimental, deshabilitada por defecto hasta completar la configuración y revisión de seguridad.

Requiere Node.js 24. Instalar dependencias con `npm ci`; usar `npm run dev` para iniciar la vista local, `npm test` para pruebas unitarias y `npm run build` para verificar la compilación. El puerto local predeterminado es 3000.

La propuesta técnica y el modelo conceptual están en `docs/arquitectura.md`; el sistema visual y el mockup aprobado están en `design-system/`. Los servicios económicos internos están en desarrollo y no están conectados a la interfaz. Los períodos de cuotas deben evaluarse con el estado histórico de la alumna en cada período.

Prisma se retiró temporalmente porque su herramienta incluía una dependencia vulnerable (GHSA-7589-6fvf-x4pw); todavía no había esquema ni integración que dependiera de ella. Antes de implementar persistencia, seleccionar e instalar versiones compatibles y sin alertas conocidas, y verificar las migraciones. PostgreSQL aún no está configurado para la aplicación.

## Base de datos: etapa inicial

Las migraciones en `db/migrations/` crean cuentas, alumnas, días de asistencia, cuotas y un historial inicial de estados. El historial registra cambios desde su instalación; para perfiles ya existentes solo registra el estado conocido al migrar. Todavía no identifica al administrador responsable y no sustituye la auditoría. Hay tablas iniciales de cargos, pagos y asignaciones con relaciones por alumna y un servicio interno experimental para registrar pagos con transacción, bloqueo, idempotencia y evento de creación. No está conectado a la aplicación ni autentica por sí mismo: el actor debe provenir de una sesión verificada y se requieren permisos de base de datos que impidan escrituras que eludan el servicio. La anulación conserva el pago y registra un evento con motivo; Existe además un ajuste individual experimental de cuotas con motivo, idempotencia y verificación del importe abonado; faltan ajustes de otros cargos y controles integrales de saldos. No utilizar para cobros reales.

Para preparar una base PostgreSQL **dedicada**, configurar `DATABASE_URL` en el entorno y ejecutar `npm run db:migrate`. El comando usa una transacción y registra nombres y sumas de verificación; un reintento no repite migraciones, y si falta o cambia una migración aplicada se detiene. La aplicación no migra automáticamente al arrancar. No aplicar a bases existentes sin evaluar su contenido y disponer de respaldo. No hay procedimiento de reversión automática; no usar en producción hasta completar el modelo y validar respaldo y restauración.

Las pruebas de integración requieren `TEST_DATABASE_URL` apuntando a una base de pruebas descartable. Ejecutar `npm run test:integration`; usan esquemas temporales y transacciones de prueba. No usar datos ni credenciales de producción. `.env.example` documenta las variables; estos comandos no cargan archivos `.env` automáticamente.
## Autenticación en desarrollo

Existen componentes internos probados para hash de contraseñas con scrypt, sesiones opacas almacenadas como hash, autorización por rol, limitación de intentos y cambio de contraseña que revoca sesiones. Las rutas experimentales de inicio, consulta y cierre de sesión están deshabilitadas por defecto; se habilitan solo con AUTH_WEB_ENABLED=true, DATABASE_URL y APP_ORIGIN explícitos. Se valida el origen en operaciones de escritura y las cookies usan HttpOnly y SameSite=Strict (Secure en producción). El límite web usa un único origen global: 20 fallos bloquean temporalmente a todos los usuarios; es necesario integrar una identificación de origen confiable antes de producción. El cambio de contraseña requiere la contraseña actual, limita intentos y revoca las sesiones. Un administrador autenticado puede restablecer experimentalmente la contraseña de una alumna con motivo auditado; aún no hay pantalla administrativa ni recuperación autónoma por correo. La contraseña temporal debe comunicarse por un canal verificado fuera de la aplicación y nunca incluirse en el motivo. Un bloqueo por intentos previos puede mantenerse hasta finalizar su ventana de 15 minutos. El formulario permanece deshabilitado mientras AUTH_WEB_ENABLED no sea true. La autorización debe comprobarse en cada operación protegida. Las pruebas actuales no sustituyen una revisión de seguridad antes de producción.

Después de migrar una base dedicada, configurar `DATABASE_URL` en el entorno y ejecutar `npm run admin:bootstrap` desde una terminal interactiva; el comando solicita el correo y la contraseña sin mostrar esta última y se niega a crear otro administrador si ya existe uno. No pasar contraseñas como argumentos ni guardarlas en archivos de configuración. El comando no habilita por sí solo el acceso web.
## Alta de alumnas en desarrollo

La ruta experimental `POST /api/admin/students` exige sesión de administrador y crea en una transacción la cuenta, el perfil, los días de asistencia, la preferencia del primer período de cuota y un evento de creación. El valor `CURRENT` o `NEXT` se calcula para el mes actual de Buenos Aires y se guarda como preferencia; todavía no genera cuotas. El generador pendiente deberá además respetar la fecha de alta, el historial de estado y las decisiones de reactivación. El listado experimental está disponible en `/admin/alumnas` y el formulario en `/admin/alumnas/nueva` para administradores autenticados; las demás secciones del menú aún no están implementadas. El acceso web continúa deshabilitado por defecto.
La ruta experimental `POST /api/admin/student-status` permite baja lógica y reactivación con sesión administrativa; la reactivación exige elegir `CURRENT` o `NEXT` y registra la elección junto al administrador. No borra cuotas ni cierra sesiones de alumnas inactivas. El generador de cuotas todavía no existe y deberá consumir el historial y los períodos registrados para aplicar estas decisiones.
El listado calcula los saldos a partir de cargos y asignaciones de pagos no anulados. «Pago parcial» indica que al menos un cargo pendiente tiene una asignación parcial; «con deuda» incluye esos casos. Una cuota sin cargo asociado o un cargo con asignaciones superiores a su importe se marca «Requiere revisión», sin mostrar un saldo concluyente. El ajuste individual de cuotas cuenta con un servicio, una ruta y una pantalla experimental; los ajustes de otros cargos y los controles integrales siguen pendientes; no utilizar estos saldos para cobros reales.
## Valores de cuota en desarrollo

La pantalla experimental `/admin/cuotas` y la ruta `/api/admin/fee-prices` permiten consultar historial y establecer el valor inicial o programar el próximo, usando centavos exactos. El valor inicial solo se permite si no hay historial ni cuotas; los cambios posteriores rigen desde el mes siguiente en Buenos Aires y conservan cada modificación. El proceso experimental de generación se describe abajo; no utilizarlo para cobros reales hasta completar la revisión de seguridad y operativa.
## Generación experimental de cuotas

El día de vencimiento se configura del 1 al 28 mediante `/api/admin/fee-due-day`; los cambios entran en vigor desde el mes siguiente y no modifican cuotas ya generadas. La pantalla experimental `/admin/cuotas` permite consultar y configurar el vencimiento cuando el acceso web está habilitado. El proceso verifica el valor y día históricos, registra cuota y cargo en la misma transacción y vuelve a examinar períodos desde un inicio explícito. Puede recuperar una cuota omitida cuando la alumna estaba activa y correspondía cobrarla, aunque luego se haya dado de baja. Considera el estado al comienzo del período y las altas o reactivaciones que eligieron cobrar ese mismo período. Si faltan configuraciones, hay cuotas sin cargo o el historial es inconsistente, se detiene para revisión.

Para pruebas en una base dedicada: configurar las migraciones, un valor inicial y un día de vencimiento, `DATABASE_URL`, `FEE_GENERATION_START` como `AAAA-MM` y `FEE_WORKER_ENABLED=true`; ejecutar `npm run fees:run` para una pasada o `npm run fees:worker` para repetirla cada hora. `FEE_WORKER_INTERVAL_SECONDS` permite entre 60 y 86400 segundos. El primer período debe contar con historial verificable de valor y vencimiento; no se inventan configuraciones anteriores. El registro de períodos y la unicidad de cuotas permiten reintentos sin duplicar cargos. Cada período se confirma por separado; si uno falla, corregir la causa y reejecutar.

El proceso no se instala ni inicia automáticamente: requiere un supervisor de procesos del entorno de despliegue que lo reinicie y alerte ante fallos, y permisos de base de datos apropiados. Un historial incoherente puede detener la recuperación completa. Revisar los resultados y las reglas con datos de prueba, completar permisos, monitoreo, respaldo y recuperación antes de producción. No usar credenciales ni datos reales para pruebas.
## Carga experimental de horno

La pantalla /admin/hornos/nueva permite agrupar piezas por alumna y confirmar una carga. El servicio verifica la sesión administrativa, valida y recalcula los importes, bloquea los perfiles, exige confirmación para alumnas inactivas y guarda carga y cargos en una transacción con clave de idempotencia. El borrador y una operación de resultado incierto se conservan en el almacenamiento local de ese navegador, por lo que no se comparten entre dispositivos y deben protegerse en equipos compartidos. La ruta GET de cargas permite consultar el historial y el detalle solo a administradores; la pantalla experimental está disponible en /admin/hornos. La pantalla experimental de historial permite corregir importes o anular piezas con motivo, confirmación e historial; identifica las piezas anuladas. No debe utilizarse para operaciones reales. Todavía faltan correcciones de datos de piezas, panel de alumna, controles de permisos de base de datos y pruebas visuales y end-to-end; no utilizar con datos reales ni para cobros.

## Catálogo experimental de materiales

La migración 018 y la ruta /api/admin/materials permiten listar, crear y editar materiales con sesión administrativa. Se registran los cambios y se rechazan ediciones sobre versiones desactualizadas. La pantalla experimental está disponible en /admin/materiales; el registro de consumos y la conservación de precios por consumo aún no están implementados. No utilizar con datos reales.
